# Architecture (as-built)

> What actually exists and how it fits together. The other harness documents sit beside this one in the plugin — operating procedure: [operations.md](operations.md). The full list of enforcement mechanisms (guardrails and gates), their limits, and how they are verified: [guardrails.md](guardrails.md) and [guardrail-verification.md](guardrail-verification.md).

## Principles

- **The SSOT is the ledger, and the ledger is reached through one adapter.** Hierarchy, dependencies, acceptance, judgment records, **and the rail and sprint registries** are all owned by the ledger, and every skill, check, hook, and script speaks to it through the plugin's `scripts/ledger.sh` — never through a backend tool directly. Which backend answers is one value, `backend` in the harness root's `ledger.json`.
- **The core asks; the backend decides the representation.** The adapter's contract is a query and a JSON shape, not a storage layout: `rails --json` answers `[{id, owner}]` and `sprints --json` answers `[{id, status}]` whatever holds them. Fix the representation in the core instead ("a sprint is an issue") and a backend with a native concept — a Jira Sprint, a Linear Cycle — has to imitate the core rather than implement the adapter.
- **Two judges.** Gates are judged **by a machine** — the evidence is an exit code. Role replies are judged **by the orchestrator**: the first-line `SIGNAL: <VALUE>` protocol narrows that reading, but **nothing enforces it** — no code parses the value, the actual judge is the model that reads the delegation result. Compliance is only seen afterwards: A9 of the plugin's `checks/transcript-check.sh` counts first lines across transcripts and reports the mismatches as violations — **violations do occur and the cycle proceeds regardless.** Impressions and self-grading are completion evidence on neither side.
- **Development-language neutral.** A target repo's build and test commands are owned by that repo's own `.harness.json`; the harness reads exit codes only.
- **The core is a plugin; everything else is machine-local or in the ledger.** Everything that is the same for every project (skills, role definitions, hooks, checks, scripts, the ledger adapter, the always-on rule block, these documents) ships as the Claude Code plugin `harness@skills`. What is left outside it is two machine-local files under the clone root and whatever the target repos own. **There is no harness repo and no harness root repo** — nothing about a harness is cloned, committed, or pushed.

## Components

| Component | Where | Role |
|---|---|---|
| Ledger pointer | `ledger.json` **directly under the clone root** (`~/.harness-workspace`), machine-local | Three keys — `backend` (`github`·`beads`·`notion`) plus what that backend needs to find the ledger (`github`: `owner`·`project`; `notion`: `database_id`; `beads`: nothing more). It is also **the marker of the harness root**: `lib/harness-root.sh` accepts a candidate only if this file sits there. No file, or a value outside the three, and every ledger call dies with rc≠0 — there is no fallback. It is not shared between machines: a wrong value shows up immediately as `ledger.sh list` answering zero rows. Written by `scripts/repo.sh root`, never by hand — the guard reserves the clone-root layer for that script |
| Ledger adapter | plugin `scripts/ledger.sh` + one `scripts/ledger-<backend>.sh` per backend | The single boundary to the ledger. Subcommands, arguments, and JSON keys are `bd`'s (`ledger.sh --help`), so a caller reads the same shape whichever backend answers; the beads-only ones (`dolt` · `where` · `export`/`import` · `sql` …) exit non-zero on `github`·`notion`. Four subcommands exist for the harness rather than for `bd`: `rails` and `sprints` (the registry queries below), `has-ui` (does this backend have a screen people read — what `scripts/board.sh` branches on, answered **without touching the ledger**), `wire-worktree` (ledger wiring of a new worktree) and `sync-check [--push]` (is the ledger ahead of its remote). Its own gate is `checks/ledger-adapter-check.sh` |
| Work ledger | `github`: issues in the target repos, gathered by one Projects v2 board · `notion`: one database · `beads`: an embedded Dolt DB under the harness root | sprint→task hierarchy, dependencies, acceptance, notes. On `github`·`notion` nothing of the ledger sits in any tree |
| Rail registry | `ledger.sh rails --json` → `[{id, owner}]` | **A rail is a person** — one rail per assignee, IDs are numbers `r1`·`r2`. A rail crosses repos; repo boundaries are the `repo:` label. **There is no registry file in the core's view** — where the answer comes from is the backend's implementation detail: `github` derives it from each epic's `rail:` label and that epic's assignee, `notion` from the page's Assignee property, `beads` reads `rails.json` under the harness root. An unregistered `rail:` label is rejected by `board-check` |
| Sprint registry | `ledger.sh sprints --json` → `[{id, status}]`, `status` ∈ `active`\|`closed` | The only source of a sprint's open/closed state — never a count of closed issues. Same split as the rail registry: `github` reads the Projects v2 Iteration field (the ID is the iteration title), `notion` a select property, `beads` `sprints.json` under the harness root. `board-check` compares it with the ledger's `sprint:` labels in both directions |
| Repo registry | `repos.json` **directly under the clone root**, machine-local + plugin `scripts/repo.sh` | **`name` and `url`, nothing else.** `repo.sh add <url>` clones and registers together; the clone location is fixed at `~/.harness-workspace/<name>` so "registered but no clone" cannot arise. Issue routing is not here — a story's `repo:` label plus the `owner` in `ledger.json` derive `owner/name`. Like `ledger.json` it is machine-local and written only by `repo.sh` |
| Target repo's own harness file | `.harness.json` at each target repo's root, git-tracked **in that repo** | The gate command (`check`), the `default_branch`, and the optional `bootstrap` run once inside a new worktree. These are commands to execute, so they belong to the repo that knows them rather than to the harness's registry — `repo.sh check <name>` is what prints the gate command, with no fallback |
| Harness plugin | `harness@skills` — source `plugins/harness/` in the skills repo; installed under `~/.claude/plugins/cache/skills/harness/<version>` | `skills/` (10 procedure skills) · `agents/` (implementer · reviewer · evaluator) · `hooks/` (`hooks.json` + SessionStart `session-context.sh`, PreToolUse `guard.sh`, PostToolUse(EnterWorktree) `enter-worktree.sh`, Stop `stop-resume.sh`) · `checks/` · `scripts/` (`ledger.sh` and its three backends · `board.sh` · `check-all.sh` · `guard-log.sh` · `ledger-migrate.sh` · `repo.sh` · `workspace-cleanup.sh`) · `lib/` (`harness-root.sh` · `worktree-name.sh`) · `docs/` (these five documents). Version in `.claude-plugin/plugin.json` |
| Always-on rules | plugin `hooks/session-context.md`, injected at SessionStart as `additionalContext` | "절대 금지" · ledger location · skill/role list · hierarchy↔ledger mapping · the table of where every other rule is owned |
| Harness root discovery | plugin `lib/harness-root.sh` | Prints the harness root in **two steps and no more**: `HARNESS_ROOT` → `${HARNESS_CLONE_ROOT:-~/.harness-workspace}`. **A candidate counts only if `ledger.json` is directly there**, and no tree is walked up — the ledger pointer is a fact about the machine, not about a tree, so the answer is the same from any cwd. It calls no backend tool (`github`·`notion` have no `bd` to ask) and fails loudly (rc=1) — never a CWD fallback |
| Worktree name derivation | plugin `lib/worktree-name.sh` | **The single place a story ID becomes a worktree name.** `EnterWorktree`'s `name` accepts only letters, digits, dots, underscores and dashes, so a `github` ID (`<repo>#<number>`) is refused as it stands: every character outside that set becomes `-` (`skills#105` → `skills-105`, branch `worktree-skills-105`). A `beads` ID passes through unchanged, which is why nothing here showed on that backend. Anything deriving a path or a branch from an ID calls this script |
| Story worktree | native `EnterWorktree` from the target clone → `~/.harness-workspace/<repo>/.claude/worktrees/<worktree name>/`, branch `worktree-<worktree name>` | Creation is the native tool's. The plugin's PostToolUse hook `enter-worktree.sh` wires the ledger through `ledger.sh wire-worktree` (on `beads`: `.beads/redirect` → the harness ledger, plus `.beads` and `.claude/worktrees/` in the clone's `.git/info/exclude`; `github`·`notion` have nothing to wire) and, when the target repo has no EnterWorktree hook of its own, runs the repo's `bootstrap` once (sibling marker `<clone>/.claude/worktrees/.bootstrapped-<name>`). A hook failure exits 2 so its stderr reaches the model (`원장 배선 실패`) |
| Worktree cleanup | plugin `scripts/workspace-cleanup.sh <story ID> [--force]` | fetch --prune → uncommitted/unpushed check → remove worktree → delete the local branch → delete the bootstrap marker. Uncommitted changes are never deleted, `--force` only skips the unpushed check. The clone stays |
| Projection renderer | plugin `scripts/board.sh all` → `<harness root>/docs/sprints/<ID>/` · `docs/backlog/` · `docs/adr/` | the ledger, read through `ledger.sh`, → a document tree people read. **It draws nothing on a backend that has its own UI** — `board.sh` asks the adapter's `has-ui` and, given a name, exits 0 having created and deleted nothing. The renderer exists for a backend with no screen of its own (`beads`, a local Dolt DB); on `github`·`notion` the ledger's own UI is the thing people read and a second copy would only diverge. Output is **outside git**. Input is every epic; the `sprint:` label only picks the output path (backlog is narrowed to `status != closed`). Descendants are gathered by the parent chain, not by label. Story directory = the `slug:` label, prefixed with the rail ID. Output is deterministic |
| Harness gates | plugin `checks/*.sh`, run as a set by plugin `scripts/check-all.sh` | What each check sees, which are wired where, and their run conditions: [guardrails.md](guardrails.md) section 3. **No harness git hook is planted anywhere** — in a target repo the ledger checks and the backend's ledger reflection are explicit steps of the cycle close (`harness:develop` "사이클 종결"), and the harness root is not a git repo at all |
| Claude Code hooks | plugin `hooks/hooks.json` — SessionStart · PreToolUse (every tool) · PostToolUse (`EnterWorktree`) · Stop | `guard.sh` fires the guardrails (four anchor-free invariants), `enter-worktree.sh` wires the ledger, `stop-resume.sh` is the **stop guard** (pushes back when this session's claimed `in_progress` work has no `VERIFY_PENDING`/`DELEGATED` mark). Runtime state lives under `${HARNESS_DATA_DIR:-~/.claude/plugins/data/harness}`; guard log and session→actor mapping under `~/.claude/` — nothing is dropped into a project tree |
| Task loop | the built-in `/loop` | Unattended repetition. Termination rules: `harness:develop` "장기 실행" |
| Version | `version` in the plugin's `.claude-plugin/plugin.json` (skills repo); history in the plugin's `CHANGELOG.md` | The only source of the number. Release procedure: the `harness:release` skill |

**What the plugin does not carry**, and therefore what a person or `repo.sh` sets up on each machine, is the list in [guardrails.md](guardrails.md) section 5 — permissions, the harness root marker, and the fact that settings and plugin versions load at session start.

## Session location and session unit

- **The harness root is machine-fixed, so where a session opens does not decide which ledger it reaches.** `lib/harness-root.sh` gives the same answer from any cwd. Planning and retrospective sessions (`harness:plan-sprint` · `harness:plan-story` · `harness:retrospective`) open at the harness root — the clone root `~/.harness-workspace`, an ordinary directory holding `ledger.json`, `repos.json`, and the clones. Development (`harness:develop` and the verify skills it calls) opens **in the clone root of the target repo**, `~/.harness-workspace/<repo>`. The plugin is installed at **user scope**, so the same skills, hooks, and rule block load in both without either place registering it.
- **The session unit is (story, repo).** A story with several `repo:` labels is worked by one session per repo, each in its own clone, each entering its own worktree. The sessions coordinate through the ledger only — the story bead's `ACTOR: <repo> <value>` notes and the tasks' claims — never through each other.
- **The harness's own core is a target repo like any other.** The plugin's source is `plugins/harness/` in the `skills` repo, which is registered in `repos.json` and cloned like every other target; a change to a skill, a check, or one of these documents is a story on that repo and goes through the same worktree and PR flow. There is nothing else to change a harness in: the registries are behind the adapter or machine-local, and the ledger is edited through `ledger.sh`.
- **Nothing about the harness is committed or shared.** `ledger.json` and `repos.json` are machine-local and written only by `repo.sh`; the projections are outside git; the ledger is remote by nature on `github`·`notion` and a Dolt remote on `beads`. A new participant installs the plugin and runs `harness:setup`, and that is the whole join.

## Multi-repo and worktrees

- A story declares its repos with `repo:<name>` labels (several allowed). Each name must be in `repos.json` and its clone must exist under `~/.harness-workspace/` — both are made by `repo.sh add`.
- The worktree is created by `EnterWorktree` from the clone; the base is the tool's, and the name is what `lib/worktree-name.sh <story ID>` prints — **not the story ID**. The branch is `worktree-<that name>`. The plugin hook wires the ledger at that moment: on `beads`, without `.beads/redirect` a bare `bd` in the worktree suggests `bd init` and following it forks the ledger.
- **A target repo's main checkout is never modified.** All implementation happens inside the worktree, and an agent checks its current path as the first action of every turn — the worktree's parent is the main checkout, one level away.
- **The worktree is outside the harness, so the harness root cannot be derived from its path.** The delegation message states the harness root absolute path; that is the only source of a subagent's `HARNESS_ROOT=<harness root> ledger.sh …`.
- The harness backlog is also managed in the ledger (`ledger.sh list -l harness`).

## Projections — artifacts outside git

Given the same ledger state, `board.sh` output is byte-identical (no timestamps). `docs/sprints/` · `docs/backlog/` · `docs/adr/` under the harness root are never committed — the ledger is the SSOT and the documents are that machine's projection. **On a backend whose own UI people already read, none of them is drawn at all**; where they are drawn, two things redraw them: the procedures (`plan-sprint` 5 · `plan-story` 7 · `develop` 4 · `verify-implement` 3) and a person's hand.

`board-check` does not look at documents — it looks at the ledger's structure. One thing a diff could never catch: the ledger hands parent labels down **only at creation**, so a decomposed backlog story pulled into a sprint later leaves its milestones and tasks unlabeled. The renderer gathers descendants by the parent chain and draws them right, but a `ledger.sh list -l sprint:<ID>` count misses them — `board-check` asserts that every descendant of a sprint-labeled epic carries the same label.
