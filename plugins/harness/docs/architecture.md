# Architecture (as-built)

> What actually exists and how it fits together. The other four harness documents sit beside this one in the plugin — operating procedure: [operations.md](operations.md). The discipline a cycle carries into any repo: [engineering.md](engineering.md). The full list of enforcement mechanisms (guardrails and gates), their limits, and how they are verified: [guardrails.md](guardrails.md) and [guardrail-verification.md](guardrail-verification.md). What does **not** ship sits in the skills repo instead — the rules for changing the harness itself (`docs/development.md`), what it is used for end to end (`docs/usecases.md`), and every check that hits plugin code with a fixture (`tests/`).

## Principles

- **The SSOT is the ledger, and the ledger is reached through one adapter.** Hierarchy, dependencies, acceptance, judgment records, **and the rail and sprint registries** are all owned by the ledger, and every skill, check, hook, and script speaks to it through the plugin's `scripts/ledger.sh` — never through a backend tool directly. Which backend answers is one value, `ledger.backend` in the repo's `.harness.json`.
- **The core asks; the backend decides the representation.** The adapter's contract is a query and a JSON shape, not a storage layout: `rails --json` answers `[{id, owner}]` and `sprints --json` answers `[{id, status}]` whatever holds them. Fix the representation in the core instead ("a sprint is an issue") and a backend with a native concept — a Jira Sprint, a Linear Cycle — has to imitate the core rather than implement the adapter.
- **Two judges.** Gates are judged **by a machine** — the evidence is an exit code. Role replies are judged **by the orchestrator**: the first-line `SIGNAL: <VALUE>` protocol narrows that reading, but **nothing enforces it** — no code parses the value, the actual judge is the model that reads the delegation result. Compliance is only seen afterwards: A9 of the plugin's `checks/transcript-check.sh` counts first lines across transcripts and reports the mismatches as violations — **violations do occur and the cycle proceeds regardless.** Impressions and self-grading are completion evidence on neither side.
- **Development-language neutral.** A target repo's build and test commands are owned by that repo's own `.harness.json`; the harness reads exit codes only.
- **The core is a plugin; everything else is in the target repo or in the ledger.** Everything that is the same for every project (skills, role definitions, hooks, checks, scripts, the ledger adapter, the always-on rule block, these documents) ships as the Claude Code plugin `harness@skills`. What is left outside it is one file per target repo — `.harness.json`, committed there. **There is no harness directory and no machine-local state** — installing the plugin and cloning a repo that carries that file is the whole setup, and the clone may live anywhere.

## Components

| Component | Where | Role |
|---|---|---|
| Target repo's harness file | `.harness.json` at the repo root, git-tracked **in that repo** | **The one file a harness needs.** The gate command (`check`), the `default_branch`, the optional `bootstrap` run once inside a new worktree, and the `ledger` object — `backend` (`github`·`beads`·`notion`) plus what that backend needs to find the ledger (`github`: `owner`·`project`; `notion`: `database_id`; `beads`: nothing more). Its presence is **the marker of the harness root**: `lib/harness-root.sh` accepts a candidate only if this file sits there. No file, or a `backend` outside those three, and every ledger call dies with rc≠0 — there is no fallback. Because it is committed, every repo of one harness carries the same `ledger` object and a clone brings the harness with it. `ledger.sh init` writes back `ledger.project`·`ledger.database_id`; everything else is written by a person |
| Ledger adapter | plugin `scripts/ledger.sh` + one `scripts/ledger-<backend>.sh` per backend | The single boundary to the ledger. Subcommands, arguments, and JSON keys are `bd`'s (`ledger.sh --help`), so a caller reads the same shape whichever backend answers; the beads-only ones (`dolt` · `where` · `export`/`import` · `sql` …) exit non-zero on `github`·`notion`. Six subcommands exist for the harness rather than for `bd`: `rails` and `sprints` (the registry queries below), `sprint-add` (the one registry **write** — it registers a sprint and never closes one), `has-ui` (does this backend have a screen people read — what `scripts/board.sh` branches on, answered **without touching the ledger**), `wire-worktree` (ledger wiring of a new worktree) and `sync-check [--push]` (is the ledger ahead of its remote). Its own gate is `tests/harness/ledger-adapter-check.sh` |
| Work ledger | `github`: issues in the target repos, gathered by one Projects v2 board · `notion`: one database · `beads`: an embedded Dolt DB at the repo that holds `.harness.json` | sprint→task hierarchy, dependencies, acceptance, notes. On `github`·`notion` nothing of the ledger sits in any tree |
| Rail registry | `ledger.sh rails --json` → `[{id, owner}]` | **A rail is a person** — one rail per assignee, IDs are numbers `r1`·`r2`. A rail crosses repos; repo boundaries are the `repo:` label. **There is no registry file in the core's view** — where the answer comes from is the backend's implementation detail: `github` derives it from each epic's `rail:` label and that epic's assignee, `notion` from the page's Assignee property, `beads` reads `rails.json` at the repo root. An unregistered `rail:` label is rejected by `board-check` |
| Sprint registry | `ledger.sh sprints --json` → `[{id, status}]`, `status` ∈ `active`\|`closed` | The only source of a sprint's open/closed state — never a count of closed issues. Same split as the rail registry: `github` reads the Projects v2 Iteration field (the ID is the iteration title), `notion` a page of its own whose Type is `sprint` (the ID is its Name, the state its Status), `beads` `sprints.json` at the repo root. Registering one is `ledger.sh sprint-add <ID>` on every backend; closing one is not — see `harness:plan-sprint` section 1 for that asymmetry. `board-check` compares it with the ledger's `sprint:` labels in both directions |
| Harness plugin | `harness@skills` — source `plugins/harness/` in the skills repo; installed under `~/.claude/plugins/cache/skills/harness/<version>` | `skills/` (9 procedure skills) · `agents/` (implementer · reviewer · evaluator) · `hooks/` (`hooks.json` + SessionStart `session-context.sh`, PreToolUse `guard.sh`, PostToolUse(EnterWorktree) `enter-worktree.sh`, Stop `stop-resume.sh`) · `checks/` · `scripts/` (`ledger.sh` and its three backends · `board.sh` · `guard-log.sh` · `workspace-cleanup.sh`) · `lib/` (`harness-root.sh` · `worktree-name.sh`) · `docs/` (these five documents) |
| Always-on rules | plugin `hooks/session-context.md`, injected at SessionStart as `additionalContext` | "절대 금지" · ledger location · skill/role list · hierarchy↔ledger mapping · the table of where every other rule is owned |
| Harness root discovery | plugin `lib/harness-root.sh` | Prints the harness root in **two steps and no more**: `HARNESS_ROOT` → walking up from the cwd to the first `.harness.json`. **That file is the discriminator**, and because the repo commits it, a worktree carries its own copy and answers itself. It calls no backend tool (`github`·`notion` have no `bd` to ask) and fails loudly (rc=1) — never a silent CWD fallback |
| Worktree name derivation | plugin `lib/worktree-name.sh` | **The single place a story ID becomes a worktree name.** `EnterWorktree`'s `name` accepts only letters, digits, dots, underscores and dashes, so a `github` ID (`<repo>#<number>`) is refused as it stands: every character outside that set becomes `-` (`skills#105` → `skills-105`, branch `worktree-skills-105`). A `beads` ID passes through unchanged, which is why nothing here showed on that backend. Anything deriving a path or a branch from an ID calls this script |
| Story worktree | common `scripts/workspace.mjs` or native Claude EnterWorktree transport | Git registration, common-dir and branch establish identity, including external linked paths. Default layout stays `.claude/worktrees/<name>`. See [workspace.md](workspace.md) for create/inspect/enter and transitional preparation results |
| Worktree cleanup | common `workspace.mjs cleanup`; compatible `workspace-cleanup.sh <story> [--force]` | Current cwd, dirty state, identity mismatch and fetch failure refuse removal. Unpushed commits refuse unless explicitly forced; only the matching registration and branch are removed. Partial progress is reported |
| Projection renderer | plugin `scripts/board.sh all` → `<repo>/docs/sprints/<ID>/` · `docs/backlog/` · `docs/adr/` | the ledger, read through `ledger.sh`, → a document tree people read. **It draws nothing on a backend that has its own UI** — `board.sh` asks the adapter's `has-ui` and, given a name, exits 0 having created and deleted nothing. The renderer exists for a backend with no screen of its own (`beads`, a local Dolt DB); on `github`·`notion` the ledger's own UI is the thing people read and a second copy would only diverge. Output is **outside git**. Input is every epic; the `sprint:` label only picks the output path (backlog is narrowed to `status != closed`). Descendants are gathered by the parent chain, not by label. Story directory = the `slug:` label, prefixed with the rail ID. Output is deterministic |
| Harness gates | plugin `checks/*.sh` (the ones a skill calls), plus the skills repo's `tests/**/*.sh`; run as a set by that repo's `tests/run-all.sh` | What each check sees, which are wired where, and their run conditions: [guardrails.md](guardrails.md) section 3. **No harness git hook is planted anywhere** — the ledger checks and the backend's ledger reflection are explicit steps of the cycle close (`harness:develop` "사이클 종결") |
| Claude Code hooks | plugin `hooks/hooks.json` — SessionStart · PreToolUse (every tool) · PostToolUse (`EnterWorktree`) · Stop | `guard.sh` fires the guardrails (four anchor-free invariants), `enter-worktree.sh` wires the ledger, `stop-resume.sh` is the **stop guard** (pushes back when this session's claimed `in_progress` work has no `VERIFY_PENDING`/`DELEGATED` mark). Runtime state lives under `${HARNESS_DATA_DIR:-~/.claude/plugins/data/harness}`; guard log and session→actor mapping under `~/.claude/` — nothing is dropped into a project tree |
| Task loop | the built-in `/loop` | Unattended repetition. Termination rules: `harness:develop` "장기 실행" |

The incremental Node configuration and process API is described in [config-process.md](config-process.md). It preserves repository-owned settings and separates legacy Bash strings from direct argv execution; entry points migrate to it individually.

**What the plugin does not carry**, and therefore what a person sets up, is the list in [guardrails.md](guardrails.md) section 5 — permissions, the repo's `.harness.json`, and the fact that settings and plugin versions load at session start.

## Session location and session unit

- **A session opens inside a target repo — that is what decides which ledger it reaches.** `lib/harness-root.sh` walks up from the cwd to the first `.harness.json`, so standing in the repo (or in one of its worktrees) is the whole addressing scheme. Planning and retrospective sessions (`harness:plan-sprint` · `harness:plan-story` · `harness:retrospective`) open at the main checkout — the work is entirely in the ledger and nothing is edited. Development (`harness:develop` and the verify skills it calls) opens there too and then enters a worktree. The plugin is installed at **user scope**, so the same skills, hooks, and rule block load without the repo registering anything.
- **The session unit is (story, repo).** A story with several `repo:` labels is worked by one session per repo, each in its own clone, each entering its own worktree. The sessions coordinate through the ledger only — the story bead's `ACTOR: <repo> <value>` notes and the tasks' claims — never through each other.
- **The harness's own core is a target repo like any other.** The plugin's source is `plugins/harness/` in the `skills` repo, which carries its own `.harness.json` like every other target; a change to a skill, a check, or one of these documents is a story on that repo and goes through the same worktree and PR flow. There is nothing else to change a harness in: the registries are behind the adapter, and the ledger is edited through `ledger.sh`.
- **The only thing a harness commits is `.harness.json`.** The projections are outside git; the ledger is remote by nature on `github`·`notion` and a Dolt remote on `beads`. A new participant installs the plugin and clones a repo that carries that file, and that is the whole join — `harness:setup` section 2 is those two commands.

## Multi-repo and worktrees

- A story declares its repos with `repo:<name>` labels (several allowed). Each name is a repo carrying `.harness.json` with the same `ledger` object; **the harness does not know where those clones are**, so a person opens a session in the one they work on. That is the cost of dropping the fixed clone location, and the session unit below is what pays it.
- Create or resume through the common workspace command; Claude’s native EnterWorktree hook connects to the same entry operation. The adapter owns ledger wiring, and the command reports preparation separately; see [workspace.md](workspace.md).
- **A target repo's main checkout is never modified.** All implementation happens inside the worktree, and an agent checks its current path as the first action of every turn — the worktree's parent is the main checkout, one level away.
- **A worktree carries its own `.harness.json`, so it answers as its own harness root.** The delegation message still states that absolute path — a subagent's `HARNESS_ROOT=<harness root> ledger.sh …` must not depend on where its cwd happens to be.
- The harness backlog is also managed in the ledger (`ledger.sh list -l harness`).

## Projections — artifacts outside git

Given the same ledger state, `board.sh` output is byte-identical (no timestamps). `docs/sprints/` · `docs/backlog/` · `docs/adr/` under the harness root are never committed — the ledger is the SSOT and the documents are that machine's projection. **On a backend whose own UI people already read, none of them is drawn at all**; where they are drawn, two things redraw them: the procedures (`plan-sprint` 5 · `plan-story` 7 · `develop` 4 · `verify-implement` 3) and a person's hand.

`board-check` does not look at documents — it looks at the ledger's structure. One thing a diff could never catch: the ledger hands parent labels down **only at creation**, so a decomposed backlog story pulled into a sprint later leaves its milestones and tasks unlabeled. The renderer gathers descendants by the parent chain and draws them right, but a `ledger.sh list -l sprint:<ID>` count misses them — `board-check` asserts that every descendant of a sprint-labeled epic carries the same label.
