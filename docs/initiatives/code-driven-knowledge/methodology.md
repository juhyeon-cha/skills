# 로드맵 구현 방법론

문서·코드·결정의 일관성을 구현하려면 **산출물의 종류에 맞는 수용 기준을 먼저 고정하고, 독립 검증의 실제 증거로 다음 단계에 진입**해야 한다. 코드 테스트 통과, 문서 형식 검사, 의미 검토, 독자 풀이를 서로 대체하지 않는다. 이 문서는 [5단계 로드맵](roadmap.md)의 개발 방법을 제안하며 아직 하네스나 배포 스킬에 구현된 절차가 아니다. 구체적인 순서와 기록 양식은 [실행 방법](execution-method.md)을 따른다.

## 기존 하네스에서 유지할 것과 보완할 것

현재 [verify-code](../../../plugins/harness/skills/verify-code/SKILL.md)는 위험에 따라 로컬·독립 검증을 선택하고, [verify-implement](../../../plugins/harness/skills/verify-implement/SKILL.md)는 명령으로 판정하지 못하는 AC를 독립 평가자에게 전달할 수 있다. 따라서 의미 검증이 불가능한 구조는 아니다. 부족한 부분은 문서 평가 입력·판정 기준·실패 분류를 재사용 가능한 계약으로 정의하는 것이다.

| 영역 | 현재 활용할 것 | 필요한 보완 |
|---|---|---|
| 실행 관리 | 스토리·태스크·담당·재시도·완료 기록 | 문서·명세·코드가 어떤 검증 경로를 거쳤는지 증거를 연결 |
| 작성 | writing-for-humans의 독자·목적 중심 작성 | 작성자가 품질 통과 여부까지 단독 결정하지 않도록 입력과 판정을 분리 |
| 문서 리뷰 | review-knowledge의 근거·결정 누락·독자 행동·불확실성 검토 | 현재 코드를 설명하는 문서와 미래 동작을 정하는 명세의 기준을 분리 |
| 문서 평가 사례 | 고정 기대 명제, 새 독자 풀이, 독립 판정, 결함 주입 | SAP 사례의 문장·질문에 묶인 부분을 계약과 사례 데이터로 분리 |
| 기계 검사 | 링크·식별자·해시·자료 구조·버전 검사 | 문서 유형별 필수 정보 누락과 증거 연결 검사; 의미 통과로 확대 해석하지 않음 |

[현재 review-knowledge 기준](../../../plugins/knowledge/skills/review-knowledge/references/rubric.md)은 현재 동작과 목표·표현 변경의 근거를 구분하며 문서 AC 계약으로 연결한다. 2단계는 이 분류를 재사용하고, 최초 생성 문서의 필수 항목 대조와 유형별 인계를 추가 검증한다. 기존 [문서 AC 실험](experiments/document-ac.md)은 이 방법의 출발 증거이며 일반 제품의 품질 보장은 아니다.

## 1. 산출물을 먼저 분류한다

| 산출물 | 권위 있는 근거 | 통과해야 할 질문 |
|---|---|---|
| 현재 동작 설명 | 고정 코드·설정·관측된 실행 | 이 버전에서 무엇이 언제 발생하며 예외와 한계를 정확히 설명하는가? |
| 목표 명세 | 사용자 지시·승인된 결정 | 필요한 동작·조건·예외·수용 기준을 구현자가 추측 없이 이해할 수 있는가? |
| 제안·설계 문서 | 문제의 증거·제약·선택지 | 사실·가정·권고·미결정을 구분하고 선택의 결과를 판단할 수 있는가? |
| 절차·직무별 안내 | 공통 정책·지원 환경·권한 | 독자가 조건에 맞는 다음 행동, 실패 대응, 중단 지점을 선택할 수 있는가? |
| 구현 코드 | 확정 목표·현재 계약 | 목표의 수용 기준을 만족하고 기존 동작의 필요한 보존 조건을 지키는가? |

한 문서가 여러 유형을 포함하면 주장이나 구간마다 구분한다. 문서 전체에 “검증 완료” 표시 하나만 붙이지 않는다. 목표 승인, 문서 품질 통과, 구현 검증 완료, 배포 확인은 별도 사실이다. 상태 의미의 원본은 [로드맵](roadmap.md#출발점과-상태의-의미)에 둔다.

## 2. 문서 품질을 관찰 가능한 조건으로 바꾼다

AC는 수용 기준이다. “읽기 좋다” 대신 독자가 무엇을 판단하거나 수행해야 하는지 정한다. 아래 기준에서 사례에 필요한 항목을 선택하되, 제외 이유를 남긴다.

| 품질 축 | 확인 방법 | 실패 예 |
|---|---|---|
| 사실·의도 일치 | 주장별로 현재 근거 또는 확정 목표와 대조 | 현재 구현되지 않은 목표를 현재 동작으로 설명 |
| 완전성 | 범위의 필수 조건·분기·예외와 문단을 대조 | 정상 경로는 있지만 실패 후 재시도 조건 누락 |
| 일관성 | 공통 정책·직무별 안내·관련 명세를 비교 | 같은 조건에서 문서마다 다른 행동 지시 |
| 실행·판단 가능성 | 문서만 읽은 독자가 시나리오를 풀고 근거 인용 | 답이 없거나 서로 다른 해석으로 행동이 갈림 |
| 검증 가능성 | 구현자 관점에서 입력·조건·기대 결과를 도출 | 목표가 “빠르게 처리”뿐이고 성공 조건 없음 |
| 추적 가능성 | 주장→근거 버전·결정, 목표→검증 결과 연결 | 현재 파일 링크만 있고 검토 당시 버전 불명 |
| 불확실성 표현 | 제안·미결정·미구현·미관측 상태를 대조 | 정적 코드 확인을 운영 환경 성공으로 설명 |
| 구성·표현 | 독자가 행동하는 순서와 용어·중복·정보 위치 검토 | 중요한 예외가 다른 문단에 숨겨져 오판 유발 |

취향 차이는 차단 사유가 아니다. 문체 지적은 영향을 받는 독자·상황·오해를 설명해야 한다. 필수 기준 하나의 실패를 평균 점수로 덮지 않는다. 적절한 “알 수 없음”은 독자에게 정답일 수 있으나, 필수 정보를 제공해야 할 문서에는 실패가 될 수 있다.

## 3. 판정 역할과 입력을 분리한다

| 역할 | 받는 입력 | 반환할 결과 |
|---|---|---|
| 기준 설계자 | 지시·근거·범위·독자·결정 | AC, 시나리오, 필수 기대 명제, 제외 범위 |
| 작성자·구현자 | 작업에 필요한 근거·목표·AC | 문서 또는 코드, 변경 이유, 미해결 항목 |
| 내용 검토자 | 실제 산출물·권위 있는 근거·AC | 사실·목표 일치, 누락·모순, 근거가 있는 지적 |
| 문서만 읽는 독자 | 정확한 문서 버전·독자 상황·질문 | 다음 행동·기대 결과·문서 인용·정보 부족 |
| 독립 판정자 | 근거·기대 명제·문서·실제 독자 응답 | AC별 판정과 실패 원인·증거 |
| 실행 조정자 | 각 역할의 실제 결과·실행 상태 | 입력 연결, 재시도·수정 배정, 최종 증거 묶음 |

역할마다 새 스킬을 만들 필요는 없다. 내용 검토와 독립 판정은 위험과 범위에 따라 한 독립 에이전트가 수행할 수 있다. 작성자가 자신의 유일한 판정자가 되지 않아야 하며, 독자 역할은 작성·판정 맥락을 공유하지 않는다. 기준 설계자는 결과를 본 뒤 정답을 맞추지 않는다. 근거가 모호한 기준은 작성 전 독립 검토로 보완하거나 미결정으로 둔다.

독자에게 코드·기대 답안·결함 이름·앞선 판정을 전달하지 않는다. 실제 전달 자료와 응답을 보존하고, 입력 분리가 프롬프트 수준인지 도구 접근까지 제한한 것인지 구분한다. 새 세션이더라도 모델의 사전 지식은 제거되지 않으므로 인용 없는 추측을 문서 품질의 증거로 쓰지 않는다. 에이전트 풀이는 사람의 이해도 실험을 대신하지 않는다.

## 4. 검증 강도를 위험에 맞춘다

- 오탈자·표현 정리는 의미·조건이 유지되는지 로컬 비교한다. 새 에이전트 평가를 매번 수행하지 않는다.
- 사실·정책·절차 변경은 형식 검사와 독립 내용 검토를 수행한다. 행동 오안내 가능성이 있는 분기는 문서만 읽는 독자 풀이를 추가한다.
- 새 문서 유형이나 평가 기준을 처음 도입할 때는 의도적 결함 검사로 평가가 작동하는지 확인한다. 이후에는 관련 기준·평가 도구가 바뀌거나 새로운 실패가 발견됐을 때 다시 수행한다.
- 문서→코드 변경은 문서 품질을 확인한 뒤 구현·코드 리뷰·동작 검증까지 진행한다. 문서 품질 통과만으로 구현 태스크를 닫지 않는다.

결함은 원본을 바꾸지 않은 사본에 넣는다. 예외 누락·반대 행동 지시·깨진 근거·미구현 목표의 완료 표현처럼 대응 AC가 있는 결함을 사용한다. 정상 문서는 통과하고 결함 문서는 해당 이유로 실패해야 한다. 결함이 통과하면 문서·기준·평가자의 어느 문제인지 조사하며 억지로 실패 판정을 쓰지 않는다.

## 5. 실패를 올바른 단계로 돌려보낸다

| 판정 | 의미 | 다음 행동 |
|---|---|---|
| 통과 | 필수 조건과 증거 충족 | 해당 범위만 다음 단계로 이동 |
| 실패 | 기대 결과와 실제 산출물 불일치 | 문서·코드·평가 입력 중 원인을 특정해 수정 후 관련 기준 재검증 |
| 판단 불가 | 정책 미결정·근거 충돌·범위 불명확 | 결정이 필요한 경우만 사용자에게 근거와 선택지 제시 |
| 미실행 | 도구·입력 접근 실패, 역할 미호출, 응답 누락 | 환경 복구 후 실제 실행; 통과로 대체하지 않음 |

이 용어는 문서 평가 결과의 의미이며 새로운 하네스 SIGNAL이 아니다. 기존 평가자 신호로의 매핑은 후속 계약에서 정한다. 재시도·진행 정체·사용자 대기 규칙은 하네스가 소유하며 별도 무한 루프를 만들지 않는다. 실패를 없애려고 기대 결과를 완화하지 않는다. 원본이나 결정이 바뀌면 기준도 새 버전으로 바꾸고 이전 실패를 보존한다.

## 6. 5단계에 적용한다

| 로드맵 단계 | 먼저 구현·확인할 방법 | 단계 진입의 증거 |
|---|---|---|
| 1. 변경 의도·실행 기반 | 유형·현재/목표 분류, AC·평가 자료 계약, 기존 코드→문서 사례 연결 | 정상·실패·미실행을 구분하고 같은 자료로 판정 근거를 추적 |
| 2. 지식·명세 구성 | 코드 없는 목표, 코드만 있는 사실, 혼합 문서의 생성·내용 검증 | 필수 정보 누락과 미구현 오표현을 검출 |
| 3. 양방향 반영 | 목표 AC에서 구현 검증으로 연결하고 코드 변경 후 설명을 대조 | 양방향 차이 해소, 구현 실패 시 목표·현재 상태 보존 |
| 4. 자동 연결 | 평가 결과를 재시도·보류·알림·원격 반영 조건에 연결 | 중복 이벤트·역방향 반복·환경 실패에서도 잘못된 완료 없음 |
| 5. 여러 저장소·고도화 | 실제 질문과 운영 실패를 평가 사례에 축적 | 근거 버전·권한·부분 완료를 구분하는 품질과 비용 측정 |

이 표는 방법의 도입 순서다. 단계 전체 완료 조건은 `stages/`가 소유한다. Promptfoo나 별도 LLM 평가 플랫폼은 먼저 만들지 않는다. 초기에는 기존 Git·JSON 자료·작은 검사 CLI·독립 에이전트로 실행하고, 5단계에서 관측된 병목에 따라 도입 여부를 판단한다.
