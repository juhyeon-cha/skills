# 변경 접수·현재/목표·평가 연결

1단계는 사용자 지시·문서·코드를 받아 현재 설명, 표현 수정, 동작 목표로 분류한다. 배포 [접수 계약](../../../../plugins/knowledge/references/intake.md)과 `intake.py`의 strict schema가 실행 입력을 정의한다. 의미 분류는 에이전트가 근거로 수행하고 CLI는 구조·참조·상태 일관성을 검사한다.

`intake`는 초기 Git 프로젝트 없이도 명시적인 `current.code:null`을 받는다. 출발점, 근거의 종류·권위·버전·위치·본문 hash, 현재 설명, 목표와 AC, 미반영 차이, 분류 이유가 하나의 불변 기록으로 연결된다. `intake-status`는 프로젝트 경로와 ID만으로 이를 재확인한다. 현재 코드 설명 경로에서는 `start --intake`가 해당 고정 커밋과 일치하는지 확인하고 실행 context에 접수 기록을 포함한다. 기존 `start --rev` 호환 경로는 접수 분류 증거를 만들지 않는다.

| 입력 | 실행 결과 | 완료 경계 |
|---|---|---|
| 확정된 현재 동작 설명 | 코드 근거의 버전과 문서 차이를 연결해 기존 작성·리뷰·적용으로 이동 | 고정 버전의 문서 갱신 |
| 문서 표현 수정 | `no_code_work` | 분류만 종료. 실제 전후 문서와 의미 보존 평가가 있어야 문서 작업 종료 |
| 사용자 지시·문서의 동작 변경 | `pending_implementation`과 목표·차이·AC 보존 | 구현 인계. 코드·배포 완료 전환 없음 |
| 제안·보류·철회 | 각각 `awaiting_decision`·`deferred`·`withdrawn` | 기존 코드→문서 실행 거부 |

명시적인 사용자 지시는 다시 승인받지 않고 confirmed로 기록한다. 기존 문서만으로 승인된 정책이라 추정하지 않는다. 근거 충돌은 내용 검토에서 결정할 문제로 남기며, 코드가 의도에 반하는 경우 문서를 코드에 맞추는 경로 대신 구현 인계를 선택한다. JSON의 authority는 주장된 권위이며 실제 사용자 승인이나 원본 진위를 인증하는 서명이 아니다. Git 원본 대조는 기존 capture/check 경로가 담당한다.

평가는 [문서 AC 계약](../../../../plugins/knowledge/skills/review-knowledge/references/document-ac.md)을 사용한다. 형식·독립 내용 검토·문서만 읽는 풀이·독립 판정은 다른 결과다. 패킷 리뷰 JSON은 그대로 유지하고 목표·표현 사례의 AC 증거는 별도 기록한다. 문서 품질, 구현, 배포 결과를 합쳐 단일 완료로 만들지 않는다.

실행 중 복구할 수 없으면 `terminate`(적용 전) 또는 `retire`(부분 적용·범위 전환 포함)로 원본을 보존한다. retire 이후 쓰기는 거부하고 새 경로의 프로젝트를 검토한 기준으로 초기화한다. 문서 자동 롤백, DB 마이그레이션, 원격 원장 동기화는 수행하지 않는다. DB 자체 손상은 디렉터리를 보존한 채 별도 프로젝트로 전환하며 retirement 성공으로 표시하지 않는다.

[조건별 판정](../experiments/foundation.md)은 실행 근거와 남은 호스트 한계를 구분한다.
