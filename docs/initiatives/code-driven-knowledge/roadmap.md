# 문서·코드·결정의 일관성 관리 로드맵

사용자 지시·문서·코드 중 어디에서 변경이 시작되더라도 의도와 현재 구현의 차이를 파악하고 필요한 쪽에 반영한다. 최종 목표는 문서·코드·결정의 일관성을 유지하고, 남은 차이와 검증 근거를 다음 개발의 판단에 사용하는 것이다.

**1단계는 고정한 18개 기준의 후속 독립 검증까지 완료했다.** [기존 최종 검증](experiments/foundation-verification.md)은 당시 macOS/Codex 개발 패키지와 독립 child 인계 범위의 완료 판정이다. 접수 원문과 리뷰 연결 및 context 손상 결함을 수정한 뒤 [18개 고정 기준](stages/01-foundation.md#승인된-고정-수용-기준)을 [새 관측과 독립 판정](experiments/foundation-followup.md)으로 모두 충족했다. PR #328과 초기 실패는 과거 증거로 보존한다. 전체는 아래 5단계이며 일정·담당·제품 도입은 아직 확정하지 않았다.

## 단계와 현재 위치

| 단계 | 사용자에게 제공할 결과 | 현재 상태 | 세부 조건 |
|---|---|---|---|
| 1. 변경 의도와 실행 기반 | 출발점·근거의 권위·현재 상태·목표 상태를 구분하고 실행을 추적 | 완료 — 지원 범위 한정 | [1단계](stages/01-foundation.md) |
| 2. 지식과 명세 구성 | 코드·문서·사용자 지시·결정에서 현재 지식과 목표 명세를 구성 | 최소 절차 구현·실측 완료; 최종 수용 판정은 실행 원장 참조 | [2단계](stages/02-bootstrap.md) |
| 3. 양방향 변경 반영 | 코드→문서와 문서→코드를 처리하고 미반영 차이를 추적 | 로컬 수용 완료 — macOS/Codex 합성 시나리오; 원격 전달·설치 활성화 별도 | [3단계](stages/03-maintenance.md) |
| 4. 개발 흐름과 자동 연결 | 개발 이벤트·정기 검사로 실행하고 필요한 예외만 사용자에게 전달 | 진행 중 — 로컬 자동화 구현·수용 관측 완료, 최종 독립 판정 전 | [4단계](stages/04-automation.md) |
| 5. 여러 저장소의 일관성 관리와 고도화 | 저장소별 목표·구현 차이를 검색·개발 판단에 활용하고 품질을 개선 | 미착수 | [5단계](stages/05-feedback.md) |

각 단계의 상세 조건과 판정 시나리오는 해당 문서가 소유한다. 다음 단계의 설계·실험은 병행할 수 있지만, 선행 조건이 미충족이면 후속 단계 완료를 선언하지 않는다. 개별 부품이 먼저 구현돼 있어도 단계 전체의 상태를 올리지 않는다.

## 출발점과 상태의 의미

| 출발점 | 처리 흐름 | 완료 판단 |
|---|---|---|
| 코드 변경 | 실제 변경 확인 → 의도·정책과 대조 → 관련 지식·문서 수정 | 의도에 반하는 코드라면 문서를 맞추지 않고 코드 수정 필요로 남긴다 |
| 문서 변경 | 표현 보완인지 동작·정책 변경인지 분류 → 목표 명세와 코드 영향 확인 → 필요한 구현·검증 | 표현만 바꾼 경우 코드 수정 없이 종료 가능하며, 동작 변경은 구현 검증까지 추적한다 |
| 사용자 지시 | 지시의 범위·의도를 기록 → 현재 상태와 차이 확인 → 문서·코드의 작업 순서 결정 | 명확한 지시를 반복 승인받지 않고, 미결정 정책이나 승인 범위만 확인한다 |

각 변경은 출발점, 사용자 지시·결정의 출처, 수정 대상, 현재 버전, 목표 명세 버전, 검증 증거를 연결한다. 현재 상태는 관측된 구현이고 목표 상태는 구현하려는 동작이다. 둘의 차이는 오류일 수도 있고 승인된 미구현 계획일 수도 있다. 기존 문서의 서술만으로 승인된 정책이라고 추정하지 않는다.

목표는 **제안 → 확정 → 구현 대기 → 구현 검증 완료**로 추적하고, 보류·철회는 별도 결과로 남긴다. 코드 수정이 불필요한 설명 변경은 그 근거를 남기고 종료한다. 문서가 승인됐다는 이유만으로 구현 완료로 바꾸지 않으며, 테스트나 실행 검증은 확인한 환경과 버전에만 유효하다. 이는 설계할 상태 의미이며 현재 CLI에 구현된 상태 목록은 아니다.

## 공통 설계 원칙

- 보존한 원본 근거(`raw`), 현재 구현에 관한 지식, 목표 명세, 독자별 설명을 구분한다. 단일 원본은 모든 내용에서 코드를 우선한다는 뜻이 아니라 각 사실·결정의 권위 있는 출처를 정하고 중복 관리하지 않는 원칙이다. 문서에서 근거 버전과 위치로 돌아갈 수 있어야 한다.
- 코드는 구현된 동작의 근거다. 의도는 사용자 지시와 승인된 명세·결정 기록에서 찾으며, 고정 커밋의 동작을 배포 환경의 동작으로 간주하지 않는다.
- CLI는 파일·버전·자료 계약·상태·반영 조건을 검사한다. 에이전트는 의미 해석·문서 작성·코드 구현·독립 리뷰를 맡고, 검증 결과로 주장 범위를 제한한다. `writing-for-humans`는 작성 책임만 가진다.
- 라이브러리는 검증된 표준 처리에 재사용한다. 스킬 수나 자체 CLI 규모를 목표로 삼지 않는다. [부품 조사](research/components-and-boundaries.md)는 후보 조사이며 도입 결정이 아니다.
- 일반적인 수정은 에이전트가 처리한다. 근거 충돌, 정책 선택, 승인 범위 변경은 근거와 영향과 함께 사용자에게 전달한다. 원격 반영·삭제·마이그레이션 승인 경계는 유지한다.
- 형식 검사와 의미 검증을 구분한다. 작성자와 독립된 리뷰, 문서만 읽는 풀이, 의도적 결함 검출을 필요한 시나리오에 적용한다. 원본 없이 성공을 주장하지 않는다.
- Promptfoo와 LLM 응답 평가 플랫폼은 전체 흐름 구현 후 5단계에서 필요성을 검토한다. 도입 자체는 완료 조건이 아니다.

## 완료를 판정하는 방법

각 조건 ID는 스토리의 수용 기준(AC: 결과가 충족해야 할 관찰 가능한 조건)으로 이어진다. 스토리 착수 시 적용 범위·고정 입력·기대 결과를 정하고 정상·실패 사례로 검증한다. 완료 보고에는 입력과 도구 버전, 실제 산출물, 독립 판정, 실패와 재개 기록, 사용자 개입 이유, 미검증 범위를 연결한다. 필수 조건의 실패나 미검증을 평균 점수로 상쇄하지 않는다.

단계 문서는 계획의 원본, `contracts/`는 현재 코드→문서 구현 계약, `experiments/`는 과거 관측이다. 태스크 실행 상태는 원장에서 관리한다. [PR #328의 K1–K5 검증](acceptance.md)은 1단계 초안의 증거로 보존하며 단계 전체의 완료 기준을 대체하지 않는다.

## 구현 방법

산출물 유형별 품질 기준·역할 분리·실패 처리는 [구현 방법론](methodology.md), 실제 작업 순서·평가 자료·AC 예시는 [실행 방법](execution-method.md)을 따른다. 기존 하네스의 실행 관리를 재사용하면서 문서 내용과 독자의 판단 가능성을 별도로 검증한다.

## 다음 작업

CLI의 장기 확장에 필요한 [명령 계약과 구버전 재개 상세 설계](design/cli-contract-and-compatibility.md)를 [후속 스토리 #345](https://github.com/juhyeon-cha/skills/issues/345)에서 진행한다. CLI·배포·자료 버전을 구분하고 오류 코드와 실제 구버전 회귀를 고정한다. 실행 파일 배포는 이번 범위에 포함하지 않는다. 목표/실행 상태, 식별자/경로, 중복 요청/원인 실행, 저장소별 부분 완료에 관한 준비 사항은 2~5단계 문서의 설계 노트를 읽는다. 노트 추가로 단계 완료 상태를 올리지 않는다.

1단계의 남은 인계 검증과 증거 보존을 마쳤다. [1단계 CLI 후속 스토리 #341](https://github.com/juhyeon-cha/skills/issues/341)은 현재 리뷰 인계, 명령 안의 Git 캡처 재사용, 상태 조회와 내부 책임 분리를 다룬다. [현재 CLI 계약](contracts/agent-workflow.md)의 회귀 검증 범위이며, 과거 18개 기준의 실제 모델 관측을 새 소스에서 재수행했다는 뜻은 아니다. 2단계는 기존 계약을 연결한 최소 절차와 합성 사례의 실제 관측을 마쳤다. 최종 수용 판정은 [실행 원장 #355](https://github.com/juhyeon-cha/skills/issues/355)를 참조한다. 문서→코드 실제 구현을 포함한 3단계는 [원본 S3-01~06과 필수 시나리오](stages/03-maintenance.md)를 로컬에서 독립 판정했다. 운영 배포·자동 이벤트 연결·여러 저장소 검증으로 확대된 결과는 아니다.
