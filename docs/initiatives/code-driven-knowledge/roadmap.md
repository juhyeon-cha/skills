# 코드 기반 지식 자동화 목표

기술 문서를 작성할 때마다 사용자가 직접 품질을 확인해야 하고, 코드가 바뀐 뒤에는 어느 근거와 문서를 갱신해야 하는지 다시 판단해야 한다. 이 문제를 **명확한 문서 수용 기준과 독립 리뷰 → 근거 기반 갱신 → 개발 흐름과의 자동 연결** 순서로 해결한다.

이 문서는 개발 범위를 정하기 위한 목표 문서다. 기간·비용을 약속하지 않고 각 단계의 완료 조건으로 다음 단계 진입을 판단한다. 실행 상태와 상세 수용 기준의 원본은 [단기 스토리 skills#323](https://github.com/juhyeon-cha/skills/issues/323)이다.

## 목표와 완료 조건

| 단계 | 목표 | 주요 산출물 | 완료 조건 |
|---|---|---|---|
| 단기 | 사용자 개입을 최소화하며 기술 문서 한 묶음을 작성·검증·수정한다 | 고정 근거, 문서 수용 기준(AC), 평가 시나리오, 공통 도메인 문서와 직무별 안내, 독립 판정 기록 | 필수 AC를 모두 통과하고, 의도적으로 결함을 넣은 문서는 해당 AC에서 실패한다. 실패 수정과 재판정 근거가 남는다 |
| 중기 | 코드 변경을 원본 이력과 현재 지식에 일관되게 반영한다 | 최초·변경 스펙 추출, 원본 근거 보존, 영향 문서 식별, 지식 갱신과 검증 절차 | 고정한 변경 전후 사례에서 영향받는 문서가 갱신되고 변경 경위와 근거를 추적할 수 있다. 재실행은 이력을 중복 누적하지 않으며 누락·충돌을 탐지한다 |
| 장기 | 개발이 지식을 갱신하고 그 지식이 다음 개발의 판단 근거가 된다 | PR 연동, 정기 검사, 여러 저장소 영향 분석, 검색·위키 제공 | 정의한 저장소와 변경 범위에서 자동 갱신·실패 재개·오래된 지식 탐지가 검증되고, 사전·사후 영향 분석이 같은 근거를 참조한다 |

## 함께 지킬 원칙

- 현재 구현은 코드와 설정에서 확인하고, 결정 배경은 승인된 결정 기록에서 찾는다. 코드만으로 의도를 만들어 내지 않는다. 특정 커밋의 동작을 배포 환경의 동작으로 간주하지 않는다.
- 원본 근거와 변경 이력인 `raw`는 추적 가능하게 보존한다. 현재 유효한 내용을 정리한 `knowledge`는 그 근거로 갱신한다. 문서에서 원본으로 돌아갈 수 있어야 한다.
- 공통 정책은 한 곳에 정의한다. 직무별 설명은 각 독자의 행동·판단에 필요한 차이를 설명하며 공통 정책을 참조한다. 사람과 AI를 위해 사실 원본을 따로 유지하지 않는다.
- `writing-for-humans`는 독자와 목적에 맞는 구성·서술을 맡는다. 원본 수집, 최신성 판단, 실행 제어는 각각의 책임으로 둔다.
- 링크·형식 검사는 의미의 정확성을 증명하지 않는다. 독립 에이전트의 시나리오 풀이도 실제 사용자의 이해도를 증명하지 않는다. 기록에는 검증한 범위와 미검증 범위를 구분한다.
- 일반적인 구성·문장 선택과 검증 실패 수정은 에이전트가 진행한다. 원본 충돌, 근거로 해결할 수 없는 정책 결정, 승인 범위 변경에만 사용자의 결정을 요청한다. 기존 원격 반영·삭제·마이그레이션 승인 경계는 유지한다.

## 단기: 문서도 AC로 검증한다

검증 사례는 [SAP Harness PR 450](https://github.com/juhyeon-cha/sap-harness/pull/450)의 AI 질문·암호 확인 흐름으로 잡는다. 앞선 검토는 커밋 `36a31860ae66c0d03b99ec244abe891a642dbdc4`를 기준으로 했다. 사례를 확보할 때 이 커밋과 파일을 확인하며, 이후 PR 변경을 섞지 않는다. SAP 연결 없이 소스를 읽어 평가할 수 있는 범위다.

작성자는 근거와 문서 AC를 받는다. 평가용 기대 답안은 문서 작성 전에 원본에서 정하고, 문서만 읽는 풀이자에게는 정답과 코드를 제공하지 않는다. 별도 판정자는 그 답변을 원본 기반 기대 결과와 비교한다. 작성자 자신의 평가만으로 완료하지 않는다.

| 평가 영역 | 관찰 가능한 통과 조건 |
|---|---|
| 사실 정확성 | 동작 주장이 고정한 코드·설정과 일치한다 |
| 조건·예외 | 범위로 정한 분기마다 조건·행동·결과가 누락 없이 설명된다 |
| 판단 가능성 | 문서만 읽은 풀이자가 필수 시나리오에 맞는 다음 행동과 결과, 근거 문단을 제시한다 |
| 근거 추적 | 주요 정책에서 근거 버전·파일·심볼로 돌아갈 수 있다 |
| 일관성 | 직무별 안내와 공통 정책이 모순되지 않는다 |
| 불확실성 | 미확정·미검증 항목을 확정된 정책이나 실행 성공으로 설명하지 않는다 |
| 검증의 유효성 | 링크 단절·식별자 변형·필수 예외 누락·잘못된 재전송 설명을 넣은 문서가 대응 AC에서 실패한다 |

예를 들어 “암호 제출로 분석 요청이 성공한 뒤 질문을 다시 전송해야 하는가?”에 대해, 문서만 읽은 풀이자는 “이미 실제 질문을 전송했으므로 다시 보내지 않는다”와 근거 문단을 제시해야 한다. 이것은 평가 형태의 예시이며 전체 평가 문항은 원본 분기를 조사한 뒤 고정한다.

착수 시에는 먼저 작은 선행 실험(M0)으로 실제 실행 표면에서 역할과 입력을 분리하고 결함을 검출할 수 있는지 확인한다. 그 결과가 나온 뒤 근거·AC 확정, 문서 작성·수정, 독립 리뷰·완료 판정의 상세 태스크를 정한다. 기존 하네스 절차와 재시도 규칙을 사용하며 새 평가 플랫폼을 먼저 만들지 않는다.

단기 결과에는 입력·기대 결과·문서 버전·풀이 답변·판정·수정 경위·남은 한계가 함께 남아야 한다. 확인된 실패가 스킬 개선을 요구할 때만 스킬을 수정한다. 관련 문제가 없는 경우 스킬을 바꾸지 않았다는 결론도 유효하다.

## 중기: 변경을 문서에 반영한다

단기에서 확인한 평가 기준을 갱신 과정에 적용한다. 최초 추출과 PR별 변경 추출을 구분하고, 승인된 결정 배경을 근거에 함께 보존한다. 변경 적용 순서, 동일 변경의 재처리, 실패 후 재개, 서로 충돌하는 근거를 다루는 규칙을 정한다.

목차는 읽을 문서를 안내하고, 근거 검색 색인은 원본의 식별자·별칭·연결 관계를 찾게 한다. 갱신된 문서와 색인이 같은 근거 버전을 참조하는지 검증한다. 자동으로 해결할 수 없는 충돌은 원본과 영향을 함께 제시한다.

## 장기: 개발과 지식을 순환시킨다

PR 병합과 정기 검사를 실행 계기로 연결한다. 개발 전에는 기존 정책과 연결 관계로 영향 범위를 확인하고, 개발 후에는 실제 변경과 결정 배경을 다시 지식에 반영한다. 검색·위키 화면은 검증된 지식의 표현으로 제공한다.

자동화 범위는 관측한 성공·실패 사례에 따라 넓힌다. 한 사례의 통과로 모든 저장소와 문서의 정확성을 보장하지 않는다. 사용자에게는 통상적인 초안 검토 대신 실제 결정이 필요한 예외를 전달하는 것을 목표로 한다.

## 범위와 진행 상태

목표 문서와 단기 스토리 등록에 이어, 고정 근거·문서 묶음·독립 풀이·결함 검출·수정 재검증을 구현했다. 관측 결과와 재실행 방법은 [단기 실험 기록](experiments/document-ac.md)에 있다. 중·장기는 방향과 단계 진입 조건이며 구현·스프린트·일정 확정이 아니다. 단기 구현 저장소는 `skills`, SAP Harness는 읽기 전용 검증 사례다. 실제 SAP 작업, 위키 배포, 원격 코드 반영은 포함하지 않는다.
