# 1단계 최종 리뷰와 검증

1단계의 S1-01~06은 **macOS/Codex 개발 패키지와 독립 child의 새 컨텍스트 인계 범위에서 충족**했다. 대상 소스는 `c9669e07e6c930d2c56cdbe49346dafbd4e6edb4`다. 독립 코드 리뷰는 LGTM, 독립 수용 평가는 MATCH다. [평가 원문](../../../../tests/knowledge/foundation-verification/acceptance.md)과 [관측 원본](../../../../tests/knowledge/foundation-verification/README.md)을 보존한다.

## 발견한 빈틈과 수정

새 에이전트가 실행을 이어받아 결과 파일을 검증하려면 문서 루트를 알아야 하는데, 공개 status에는 해당 설정이 없었다. `knowledge.py status`의 프로젝트·실행 응답에 `project`와 `settings`를 추가했다. 이제 저장소·문서 루트, 범위, 독자와 목적을 공개 응답에서 확인할 수 있다. 이전 소스에 새 회귀 검사를 적용하면 `KeyError: settings`로 실패하고 수정 후 통과했다.

## 실제로 관측한 흐름

개발 저장소 밖에 최종 toolkit 패키지를 복사하고 Python 3.14.7·jsonschema 4.26.0으로 doctor, init, start를 실행했다. 패키지 61개 파일의 해시를 현재 소스와 대조했다. 같은 패키지·프로젝트에서 다음 흐름을 진행했다.

1. 첫 코드 변경 B의 잘못된 설명을 독립 리뷰가 반려했다. 성공 시 조기 반환, ConnectionError 조건과 다른 오류 전달 설명을 새 작성자가 보완하고 새 패킷의 독립 리뷰가 통과했다.
2. B 반영 뒤 기준을 승계한 변경 C를 새 작성자·리뷰어가 처리했다. 최종 설명은 최대 5회 시도와 오류 전달 조건을 담는다.
3. C의 문서 반영 직후 exit 91을 주입했다. `applying`과 이전 기준이 남은 상태에서 새 컨텍스트 child가 프로젝트·실행 ID와 설치 런타임 좌표를 받아 공개 status/resume로 완료했다. 내부 DB 조회나 자료 인자 재조립은 필요하지 않았다.
4. 코드 접수는 문서 갱신 경로, 문서의 동작 변경과 사용자 목표는 `pending_implementation`, 표현 수정은 `no_code_work`로 분류했다. 실제 구현·배포 완료를 주장하지 않았다.

최종 상태는 완료 실행 2개, 활성 실행 없음이다. 최종 기준은 `e9aac096b0d8b01ef3f2aae55f9bf0006fd527e0`, 문서 SHA256은 `cab4d67a4f8644465f84e9ae6868cee3e8175aee4df4361f5bf3b0fff2381a29`다. 소스 작업 디렉터리가 B 상태여도 CLI와 검토자는 고정한 C 커밋을 읽었다.

## 회귀와 관측의 구분

서로 다른 회귀 66개가 통과했다. source-contract의 변경 없는 37개와 document-ac 7개는 `51e9b17` 결과를 재사용했고, 변경된 project 12개와 measurement 10개는 최종 소스에서 실행했다. `foundation-check.sh`도 통과했지만 저장 응답 재생은 새 모델 호출로 세지 않는다. 독립 평가자는 project 12개, 고정 문서 바이트 검사와 패키지 해시를 직접 재확인했다. 명령·버전·재사용 범위는 원본의 `roles_and_checks["checks.json"]`에 있다.

새 역할 호출의 전달문·반환과 공식 등록·완료 기록을 보존했다. 역할 출처는 부모의 실제 도구 관측이며 native 역할 강제는 아니다. 이전 [초기 보완 실패](foundation.md)와 [측정 실행기 미실행](../../../../tests/knowledge/measurement/README.md)은 그대로 남겼다. 이번 관측은 공개 CLI를 별도로 조정한 실행이며 측정 실행기 workflow 사례의 성공으로 바꾸지 않는다.

## 검증하지 않은 범위

전체 `tests/run-all.sh`, marketplace 자동 로딩·업데이트, 앱 재시작, 새 최상위 데스크톱 작업, 다른 OS, native 역할 강제, 사람 사용성, 일반 문서 정확성과 실제 서비스 구현·배포는 검증하지 않았다. 새 컨텍스트 인계는 `fork_turns: none`의 독립 child로 관측했다. 설치본 가드·플러그인 코어는 수정하지 않았으며 사용자 추가 개입이나 원격 쓰기 없이 완료했다. 2단계는 미착수이며 문서→코드 실제 구현은 3단계 범위다.
