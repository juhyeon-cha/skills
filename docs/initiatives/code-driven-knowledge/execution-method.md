# 문서·코드 변경의 실행 방법

[방법론](methodology.md)을 실제 스토리로 옮기는 절차다. 현재는 설계이며 아래 자료 이름·역할 연결·결과 형식을 새 공개 CLI나 하네스 기능으로 구현한 상태는 아니다. 실행 상태는 기존 하네스 원장이 소유하고, 평가 자료는 버전과 근거를 보존한다.

1단계의 개발 소스를 릴리스 없이 측정할 때는 [개발 실측 실행기](../../../tests/knowledge/measurement/README.md)를 사용한다. 코드 갱신 흐름과 문서 AC의 고정 사례를 지원하며, 아래 전체 설계나 이후 단계의 범용 실행기를 구현한 것은 아니다.

## 1. 변경 계약을 작성한다

사용자 요청을 기존 맥락에서 해석하고 불명확한 정책만 확인한다. 아래 항목을 스토리의 본문 또는 연결된 문서에 남긴다.

| 항목 | 필수 내용 |
|---|---|
| 변경 식별 | 요청·관련 결정, 출발점, 대상 문서·코드, 범위와 제외 |
| 독자와 행동 | 누가 어떤 판단·작업을 해야 하는가 |
| 현재와 목표 | 현재 근거 버전, 목표 명세 버전, 제안·확정 여부, 미반영 차이 |
| AC | 조건 ID, 적용 유형, 상황·입력, 필수 기대 결과, 근거, 검사 방법 |
| 완료 범위 | 문서 품질 완료인지 구현 검증까지인지, 환경과 원격 반영 경계 |

명확한 사용자 지시를 형식적으로 재승인받지 않는다. 표현 수정은 코드 영향 없음의 근거를 기록하고 좁게 처리한다. 문서 선행 동작 변경은 목표를 먼저 검증하고 구현할 작업을 연결한다.

## 2. 평가 입력을 고정한다

코드·문서·결정에서 권위 있는 근거를 선택하고 범위·버전·발췌를 기록한다. 작성 전에 질문과 필수 기대 명제를 정한다. 작성자에게 일반 AC를 제공하되 독자에게는 문서와 질문만 제공한다. 검증 유형별 입력 권한은 [역할 표](methodology.md#3-판정-역할과-입력을-분리한다)를 따른다.

근거로 기대 결과를 정할 수 없다면 “정보 부족”을 통과 답안으로 설정할 수 있는지 먼저 판단한다. 필수 정책 자체가 없는 경우에는 결정이 필요하다. 코드와 다르다는 이유로 승인된 목표의 기대 결과를 현재 코드에 맞추지 않는다.

## 3. 작성하고 빠르게 검사한다

작성자는 writing-for-humans로 문서를 작성하거나 수정한다. 로컬 검사로 파일·링크·식별자·버전·필수 자료 연결을 확인한다. 검사 실패를 먼저 해결하되 CLI 종료 코드가 문서 의미의 통과를 뜻하지 않도록 결과 종류를 분리한다.

기존 `tests/knowledge/document-ac/check.py`와 `packets.py`는 특정 사례의 검증·입력 준비 도구다. 그대로 범용 검사기로 주장하지 않는다. 재사용하려면 사례별 필수 명제와 검사 로직을 분리하고 다른 유형의 정상·결함 사례로 확인해야 한다.

## 4. 독립 내용 검토와 독자 풀이를 수행한다

내용 검토자는 주장·조건·예외·목표 상태를 근거와 대조한다. 독자 풀이가 필요한 변경은 작성 이력이 없는 별도 실행에 고정 문서와 질문을 전달한다. 독자는 행동·결과·문서 인용을 반환하며 정보가 없으면 없다고 답한다.

독립 판정자는 실제 응답과 필수 명제를 비교한다. 틀린 문서의 정확한 인용은 사실성 실패이고, 정답만 맞고 문서 인용이 없는 답변은 증거 부족이다. 문서 누락과 독자의 인용 누락을 분리해 기록한다. 역할 호출이나 결과가 없으면 미실행이지 통과가 아니다.

새 평가 기준은 정상본과 의도적 결함 사본으로 확인한다. 이 절차를 실제 수행하기 전에는 “독립 검증 완료”라고 쓰지 않는다.

## 5. 수정과 재검증을 연결한다

실패한 AC·해당 문단·근거·독자의 실제 응답을 작성자에게 전달한다. 문서 변경 뒤에는 새 문서 버전으로 관련 내용 검사와 새 독자 풀이를 수행한다. 공통 정책을 바꿨으면 이를 참조하는 직무별 문서까지 검사한다. 이전 응답을 새 문서 버전의 결과로 재사용하지 않는다.

재검증 범위는 변경된 주장과 그 의존 관계로 정한다. 기준이나 근거가 바뀌지 않은 무관한 검사를 반복하지 않는다. 기준 변경이 필요하면 변경 이유와 이전 판정을 남기고, 작성 결과에 맞춘 완화가 아닌지 독립 검토한다.

## 6. 코드 구현과 차이 해소를 판정한다

목표 명세가 있는 경우 문서 품질 통과 뒤 기존 하네스 구현·코드 리뷰·동작 검증 절차로 연결한다. 목표 AC별 검증 결과를 붙이고 문서의 현재 동작 설명도 실제 결과와 대조한다. 목표와 구현이 다르면 문서·코드·목표 결정 중 수정할 대상을 근거로 정한다.

코드 구현 실패는 승인된 목표를 지우는 이유가 아니다. 구현 대기·실패와 미반영 차이를 보존한다. 코드 변경이 원래 의도에 반하면 문서를 잘못된 코드에 맞추지 않는다. 모든 필수 목표가 해당 환경에서 검증돼야 구현 차이 해소로 판정한다. 배포 확인은 별도 증거가 있을 때만 기록한다.

## 7. 증거를 묶고 기존 완료 절차로 전달한다

검증 묶음은 최소한 다음 관계를 복원할 수 있어야 한다. 저장 형식은 후속 구현에서 정하며 새로운 업무 원장을 만들지 않는다.

| 기록 | 내용 |
|---|---|
| 입력 | 요청·근거·목표·문서 버전, 해시, 역할별 실제 전달 자료 |
| 기준 | AC와 질문, 필수 기대 명제, 제외 이유, 기준 변경 이력 |
| 실행 | 실제 역할 식별자, 관측 가능한 도구·모델 정보, 접근 제한·실패; 모르는 값은 미확인 |
| 결과 | 원문 응답, 기계 검사 결과, AC별 판정과 인용·근거, 결함 검출 결과 |
| 수정 | 실패 원인, 수정 버전, 재검증 범위·결과 |
| 완료 | 문서·구현·배포별 판정 범위, 남은 차이, 사용자 개입과 미검증 항목 |

기존 `verify-implement`에 이 증거를 전달해 AC를 판정한다. 문서 품질 결과만으로 코드·배포까지 완료 처리하지 않는다. 이번 설계에서 원장 필드나 SIGNAL을 새로 확정하지 않는다.

## 구체적인 AC 예시

예시는 후속 스토리 작성 형태를 보여주며 현재 제품 정책이나 구현 결과가 아니다.

| ID | 상황·유형 | 필수 기대 결과 | 검증 |
|---|---|---|---|
| DOC-01 | 현재 코드가 연결 오류에만 총 3회 시도 | 현재 동작 문서는 최초 시도 포함 여부와 재시도하지 않는 오류를 설명 | 고정 코드 대조 + 독자의 횟수·예외 답변과 인용 |
| SPEC-01 | 사용자가 총 4회로 변경하도록 지시, 코드는 아직 3회 | 목표 문서는 4회와 적용 조건을 명세하고 구현 대기를 표시 | 지시 대조 + 독립 명세 검토; 현재 코드와 다르다는 이유로 실패시키지 않음 |
| CODE-01 | SPEC-01을 구현 | 지정 오류에서 총 4회, 제외 오류에서는 즉시 전파 | 해당 동작 테스트·독립 코드 리뷰, 목표 버전 연결 |
| NEG-01 | 목표 문서 사본에서 구현 대기 표시를 지우고 현재 동작이라고 표현 | 현재 사실·목표 구분 기준에서 실패 | 독립 내용 판정; 실패 이유와 실제 응답 보존 |

## 구현할 작업의 순서

1. **분류·평가 계약:** 현재/목표/제안·절차 유형, 역할별 입력, AC·결과 자료를 정의한다. 기존 CLI 상태와 목표 상태의 차이도 명시한다.
2. **세 사례 연결:** 현재 코드 설명, 코드 없는 목표 명세, 표현만 수정하는 문서를 같은 계약으로 평가한다. 정상·결함·미실행 결과를 구분한다.
3. **범용화 경계 검증:** 실제 사례에서 반복된 자료 준비·기계 검사를 CLI로 분리하고 내용 판단은 에이전트에 둔다. 필요한 스킬 책임은 여기서 결정한다.
4. **양방향 구현 인계:** 검증된 목표를 구현 태스크와 연결하고 실제 테스트·리뷰 결과로 차이를 해소한다.
5. **운영 연결과 고도화:** 4·5단계의 이벤트·검색·운영 요구에 맞춰 재사용한다. Promptfoo와 별도 평가 플랫폼은 그때 검토한다.

다음 스토리는 1단계의 분류·평가 계약과 세 사례 검증으로 제한하는 것을 권장한다. 이번 문서는 구현 방법의 설계이며 하네스 코어 수정이나 새로운 평가 플랫폼 구현을 수행한 결과가 아니다.
