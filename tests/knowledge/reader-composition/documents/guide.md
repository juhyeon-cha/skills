# 주문 취소를 구현하고 판단하기

주문을 취소한 사람이 알고 싶은 것은 요청을 눌렀다는 사실이 아니라, 자신의 주문이 실제로 취소 상태가 되었는지다. 이번 합성 시나리오에는 고객 두 명이 취소 여부를 상담원에게 물었다는 제보가 있다. 이를 배경으로 자기 주문의 취소 상태를 직접 확인하는 제한된 기능을 우선 검토한다. 다만 문의 규모나 감소 효과는 아직 입증되지 않았다.

이 안내는 화면 개발자(FE), 서버 개발자(BE), 기획자, 제품 책임자(PO)가 동일한 조건에서 동일한 결과를 기대하도록 돕는다. **정적 구현**은 제공된 Python 코드의 동작이고, **가상 확정 범위**는 의사결정 자료 P1의 정책이다. **검토안·지표 후보**는 D1에 기록된 제품 제안이다. 실제 서비스의 승인·관측·실행·배포를 뜻하지 않는다. 독립 문서 검토도 아직 대기 중이다.

## 공통 규칙

취소는 주문 상태의 변경이고, 환불은 결제 금액을 돌려주는 별도의 작업이다. 이 구분을 놓치면 주문 화면의 성공 문구를 고객의 환불 완료로 잘못 안내하게 된다.

> [!CARDS] 범위와 결정의 경계
>
> - **가상 확정 범위 P1** — 본인의 결제 완료 주문을 취소 상태로 바꾼다. 이미 취소된 본인 주문의 반복 요청은 완료로 응답한다. 출고 이후 취소는 제외한다.
> - **범위 밖인 환불** — 결제사 연동과 실제 환불은 이번 단계에 포함되지 않는다. 취소 완료 문구와 성공 응답은 환불 성공을 뜻하지 않는다.
> - **미정인 운영 인계** — 환불 제공 시점과 운영 처리 주체가 정해지지 않았다. 환불 정책이 확정되기 전에는 이 기능으로 고객에게 환불 완료를 약속할 수 없다.

서버의 정적 구현은 아래 순서로 조건을 검사한다. `paid`는 결제 완료, `cancelled`는 취소 완료를 뜻한다. 아래 표는 화면의 진입 조건과 별개로 서버 호출 자체가 받는 결과를 정의한다.

| 서버가 확인하는 조건 | 반환값 | 주문 데이터 변화 |
|---|---|---|
| 소유자가 요청자와 다름 | `status: 403`, `code: FORBIDDEN` | 변경 없음. 타인 주문은 이미 취소된 경우에도 이 행이 먼저 적용됨 |
| 본인 주문이며 이미 `cancelled` | `status: 200`, `state: cancelled` | 새 변경 없이 완료 응답 |
| 본인 주문이며 `paid`도 `cancelled`도 아님 | `status: 409`, `code: NOT_CANCELLABLE` | 변경 없음. 출고 상태도 이 조건에 해당 |
| 본인 주문이며 `paid` | `status: 200`, `state: cancelled` | 메모리 주문 상태를 `cancelled`로 바꾼 뒤 응답 |

정책 근거는 [P1 원문](evidence.md#의사결정-원문), 현재 검사 순서와 반환값의 근거는 [서비스 원문](evidence.md#서비스-원문)이다. 코드에서 확인되는 처리 방식은 설명할 수 있지만, 팀이 이 정책을 선택한 역사적 사업 이유까지 코드로 추정하지 않는다. 해당 이유는 입력에 없다.

## 화면에서 사용자가 겪는 흐름

화면의 취소 요청은 본인 주문이고 `paid`이며 요청 진행 중이 아닐 때만 허용한다. 정적 함수 `can_cancel`은 이 세 조건이 모두 맞을 때 참이다. `pending`은 요청 진행 중인지 나타내는 값이다. `pending`이 참인 동안에는 추가 클릭으로 취소를 다시 요청하지 않도록 이 판정을 적용한다. 실제 버튼 연결과 `pending` 갱신 코드는 제공되지 않아 UI에서 차단이 동작한다는 실행 증거는 없다.

아래는 취소 가능한 화면에서 시작하는 **요청 1회의 결과 안내 흐름**이다. 진입 조건을 만족하지 않으면 이 흐름의 요청을 시작하지 않는다. 서버 결과별 안내는 현재 `outcome` 함수에 근거하며, 운영 환경의 통신 처리가 검증되었다는 뜻은 아니다.

> [!FLOW] 취소 요청과 결과 안내
>
> 1. 진입 조건인 본인 주문·결제 완료·요청 대기 없음이 맞는지 확인한다.
> 2. 사용자가 취소를 요청한다. 진행 중에는 추가 요청을 허용하지 않는다.
> 3. 받은 응답 또는 응답 없음에 따라 다음 행동을 안내한다.
>    - **200 · 취소 완료** — ‘주문 취소 완료’를 보여주고 ‘목록으로 이동’을 안내한다. 환불 완료 의미는 아니다.
>    - **403 · 권한 거절** — ‘취소 권한 없음’을 보여주고 ‘계정 확인’을 안내한다.
>    - **409 · 상태 거절** — ‘취소 가능한 상태가 아님’을 보여주고 ‘주문 다시 조회’를 안내한다.
>    - **응답 없음 · 결과 미확정** — ‘처리 결과 확인 필요’를 보여주고 ‘주문 다시 조회’를 안내한다. 성공·실패를 단정하지 않는다.
>    - **그 밖의 응답 상태 · 결과 확인 필요** — ‘처리 결과 확인 필요’를 보여주고 ‘주문 다시 조회’를 안내한다.

정상 경로를 예로 들면 본인의 결제 완료 주문에서 요청하고, 서버가 상태를 바꾼 뒤 보낸 200 응답을 화면이 받으면 완료를 안내한다. 반면 **상태 변경 뒤 응답만 유실된 경우**를 가정하면 서버에는 취소 상태가 남아 있어도 화면은 그 사실을 알 수 없다. 응답이 없다는 사실만으로 서버의 변경 여부를 판별할 수 없기 때문에 재조회로 결과를 확인하도록 안내한다. 이는 원문의 정책과 구현을 설명하는 가정 시나리오이며 실제 장애 관측은 아니다.

403은 요청자의 권한을 확인해야 하는 상황이고, 409는 주문의 현재 상태를 확인해야 하는 상황이다. 그래서 전자는 계정 확인, 후자는 주문 재조회로 안내가 갈린다. 응답 유실 시 자료가 정한 다음 행동도 재조회이며 자동 재취소를 약속하지 않는다. 재조회 API와 그 결과를 받은 후의 구체적인 화면 전환은 입력에 없어 연결 구현이 남아 있다. 근거는 [화면 원문](evidence.md#화면-원문)과 [P1](evidence.md#의사결정-원문)이다.

## 호출자와 데이터의 계약

서버 구현자는 [공통 규칙](guide.md#공통-규칙)의 반환값뿐 아니라 검사 순서를 보존해야 한다. 소유권 검사가 취소 상태 검사보다 먼저이므로 타인의 취소 완료 주문도 성공으로 반환되지 않는다. 화면에서 요청을 막는 판정만으로 이 서버 검사를 대신할 수는 없다.

반복 요청은 별도의 요청 식별자를 저장해 구분하지 않는다. 이 코드에서는 해당 주문이 이미 `cancelled`인지 검사해 완료를 반환한다. 따라서 같은 본인 주문에 최초 호출이 상태 변경을 마친 뒤 다시 호출하면 완료 응답을 받는다. 화면에서 이미 취소된 주문의 신규 요청을 허용하지 않는 것과 서버가 반복 호출에 완료를 반환하는 것은 서로 다른 경계의 동작이다.

`Orders` 객체는 하나의 `Lock`으로 주문 조회부터 권한·상태 검사와 변경까지 감싼다. 같은 객체의 잠금을 공유하는 호출은 이 구간을 순서대로 처리하므로, 뒤의 호출은 앞선 호출이 변경한 상태를 확인할 수 있다. 보장 근거는 **한 객체의 메모리 잠금 범위**다. 여러 `Orders` 객체, 여러 프로세스나 서버 사이의 경쟁, 영속 저장소의 트랜잭션 보장으로 확장할 수 없다.

상태는 전달받은 메모리 사전에 저장되며 영속 저장소와 결제사 연동은 없다. 따라서 200은 [공통 규칙](guide.md#공통-규칙)의 상태 결과만 나타낸다. 프로세스 재시작 후 보존, 실제 API 연결, 통신 복구, 운영 동시성, 환불 실행과 배포는 이번 정적 검토로 입증되지 않았다. 근거는 [서비스 원문](evidence.md#서비스-원문)이다.

## 정책을 수용 시나리오로 옮기기

기획자는 고객의 주문 상태 확인과 환불 처리를 구분한 채 흐름을 정의한다. [공통 규칙](guide.md#공통-규칙)의 신규 취소·반복 요청·출고 이후 요청은 서로 다른 시작 상태다. 이 차이를 지우고 모두 ‘취소 버튼을 누르면 완료’로 쓰면 제외 범위와 반복 호출 계약을 검증할 수 없다.

| 수용 시나리오의 시작과 행동 | 관찰할 결과와 경계 |
|---|---|
| 본인의 `paid` 주문으로 신규 요청 | 공통 규칙의 상태 변경과 성공 반환이 모두 나타나는지 확인 |
| 본인의 이미 `cancelled`인 주문에 서버 반복 요청 | 새 변경 없이 동일 완료 결과인지 확인. 화면에 반복 요청 버튼을 추가하라는 요구는 아님 |
| 본인 주문이 출고 상태일 때 서버 요청 | 공통 규칙의 상태 거절 결과이며 주문 상태가 유지되는지 확인 |
| 요청 후 화면에 응답이 도착하지 않음 | 화면 흐름의 미확정 안내와 재조회 행동이 나타나고 성공·실패를 단정하지 않는지 확인 |
| 이미 취소된 타인 주문으로 서버 요청 | 상태에 앞서 권한 거절이 적용되는지 확인 |

이는 관찰 가능한 수용 조건을 문서화한 것이며 테스트 통과 기록이 아니다. 재조회까지 이어지는 실제 복구 흐름은 API·화면 연결 근거가 없어 검증 대기다. 환불 문의가 이어질 때 누구에게 언제 넘기는지도 [운영 인계의 미정 사항](guide.md#공통-규칙)에 해당한다. 상담원의 역할이나 처리 기한을 임의로 확정할 수 없다.

## 범위와 성과를 판단하기

PO가 지금 판단할 대상은 취소 상태 확인이라는 제한된 검토안과 환불까지 함께 제공하는 대안의 차이다. O1의 근거는 합성 시나리오에서 고객 두 명이 취소 여부를 문의했다는 제보뿐이다. 발생 빈도, 전체 고객 비율, 상담 비용, 기존 전환율은 측정하지 않았고 상담 문의 감소 효과도 입증되지 않았다. 제보는 확인할 문제를 가리키지만 문제의 규모나 투자 효과를 정량화하지는 못한다.

| 자료에 기록된 선택지 | 제공하려는 범위 | 판단을 바꾸는 의존성 |
|---|---|---|
| D1의 우선 검토안 | 자기 주문의 취소 상태를 직접 확인하는 제한된 기능 | P1의 구현과 결과 안내 범위 내에서 검토. 환불 제공 약속은 포함되지 않음 |
| 환불까지 한 번에 제공하는 대안 | 취소와 결제 환불을 함께 제공 | 외부 결제사 연동과 환불 정책 결정이 더 필요 |

두 선택지의 구현 비용·일정 비교나 우선 검토안을 고른 상세 사업 판단 근거는 자료에 없다. 코드의 단순함을 비용 우위나 투자 승인 이유로 바꿔 쓰지 않는다. 환불 대안은 검토에 필요한 의존성이 제시되었을 뿐, 실제 구현 승인이나 배제 결정으로 읽을 수 없다.

성과 지표 후보는 ‘취소 결과 관련 문의 비율’이다. 아직 분모·관측 기간·목표치가 정해지지 않았으므로 이를 먼저 정의하고 실제 관측 근거를 확보해야 달성 여부를 판정할 수 있다. 환불 대안을 채택하려면 공통 규칙에 적은 시점·운영 주체와 결제사 연동 문제도 해결해야 한다. 출시 일정과 출시 승인은 자료에 없다. [구현 검증 경계](guide.md#호출자와-데이터의-계약)도 남아 있어 이 문서만으로 출시 준비 완료를 선언할 수 없다. 근거는 [O1과 D1 원문](evidence.md#의사결정-원문)이다.

## 문서의 근거와 상태

이 문서는 변경되지 않은 합성 입력 v1을 읽어 만든 새로운 설명이다. 입력과 문서의 버전을 구분하며, 독립 검토·렌더링·실제 실행 검증은 대기 상태다. [근거 페이지](evidence.md#근거와-검증-경계)에 검사한 원문과 SHA-256을 기록했다. 이 안내 본문만으로 질문의 조건과 결과를 판단할 수 있으며, 근거 페이지는 출처 확인용이다.
