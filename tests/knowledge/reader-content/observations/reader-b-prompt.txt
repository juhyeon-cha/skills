# 주문 취소: 구현·수용 조건과 제품 판단

이번 평가의 문제는 취소 여부를 알 수 없는 사용자가 결과를 확인할 수 있게 하는 것이다. 검토 대상은 본인 주문의 취소 상태 변경과 결과 안내이며, 환불 제공 여부는 별도의 결정이다. FE(화면 개발), BE(서버 개발), 기획, PO(제품 책임자)는 아래 공통 규칙으로 구현·수용 시나리오·범위를 판단한다.

이 문서는 **합성 평가 자료**만 설명한다. ‘현재 동작’은 Python 코드를 정적으로 읽은 결과이며 실제 API 실행·운영·배포 확인이 아니다. ‘확정 범위’는 가상 의사결정 P1의 확정 사항이고, 실제 서비스 승인으로 해석할 수 없다. D1의 우선 검토안과 지표 후보는 제품 제안이며 출시 결정이 아니다.

<a id="shared"></a>
## 1. 공통 규칙: 취소와 환불

P1의 확정 범위는 본인 주문의 `paid`(결제 완료)를 `cancelled`(취소 완료)로 바꾸는 것이다. 이미 취소된 본인 주문은 반복 요청에도 취소 완료로 응답한다. 출고 이후 취소는 제외한다. 현재 서비스 코드의 처리 순서는 다음과 같으며, 기획의 수용 시나리오도 이 표의 조건과 관찰 결과로 구분한다.

| 조건·검사 순서 | 현재 코드의 결과 / 수용 시 관찰할 결과 |
|---|---|
| 주문 소유자와 요청자가 다름 | 상태 검사에 앞서 `{'status': 403, 'code': 'FORBIDDEN'}` 반환. 이미 취소된 타인 주문도 동일하다. 상태를 바꾸지 않는다. |
| 본인 주문이 이미 `cancelled` | `{'status': 200, 'state': 'cancelled'}` 반환. 새 취소 변경 없이 완료 응답을 받는다. |
| 본인 주문이 `paid`도 `cancelled`도 아님 | `{'status': 409, 'code': 'NOT_CANCELLABLE'}` 반환. 상태를 바꾸지 않는다. 출고 상태가 입력된 경우도 여기에 해당한다. |
| 본인 주문이 `paid` | 메모리의 주문 상태를 `cancelled`로 바꾼 뒤 `{'status': 200, 'state': 'cancelled'}` 반환. |

‘취소 완료’는 **주문 상태의 변경**이다. 결제사 연동과 실제 환불은 P1 범위 밖이며, 취소 성공 응답이나 화면 완료 문구가 환불 성공을 뜻하지 않는다. 환불 제공 시점과 운영 처리 주체는 미정이다. 환불 정책이 정해지기 전에는 이 기능으로 고객에게 환불 완료를 약속할 수 없다.

근거: [service.py 10–21행](../fixture/service.py), [decisions.md P1, 5–13행](../fixture/decisions.md). 정책의 근거는 P1이고, 코드는 현재 구현 근거다.

## 2. 화면: 요청 가능 조건과 결과별 다음 행동

현재 `can_cancel`은 [공통 규칙](#shared)의 신규 취소 대상이면서 `owner == viewer`, `pending == False`일 때만 참이다. 요청 진행 중(`pending == True`)에는 추가 클릭으로 취소 요청을 허용하지 않는다. 화면 구현 시 이 반환값을 요청 가능 여부에 적용해야 한다. 실제 버튼 연결이나 `pending`을 설정·해제하는 이벤트 코드는 제공되지 않았으므로 실제 중복 클릭 차단이 검증된 것은 아니다.

현재 `outcome`이 정하는 안내와 행동은 아래와 같다.

| 받은 결과 | 사용자 안내 | 다음 행동 |
|---|---|---|
| `200` | ‘주문 취소 완료’ | ‘목록으로 이동’ |
| `403` | ‘취소 권한 없음’ | ‘계정 확인’ |
| `409` | ‘취소 가능한 상태가 아님’ | ‘주문 다시 조회’ |
| 응답 없음(`None`) | ‘취소 실패’ | ‘즉시 자동 재요청’ |
| 위에 없는 응답 상태 | ‘처리 결과 확인 필요’ | ‘주문 다시 조회’ |

403은 권한 문제이므로 계정을 확인하고, 409는 현재 주문 상태 문제이므로 주문을 다시 조회한다. 응답이 없으면 취소가 실패한 것으로 확정한다. 주문을 재조회할 필요 없이 즉시 자동 재요청한다.

기획의 응답 유실 수용 시나리오는 요청 후 응답이 없을 때 취소 실패 문구가 보이고 자동 재요청이 즉시 수행되는지 관찰하는 것이다.

근거: [screen.py 4–17행](../fixture/screen.py), [decisions.md P1, 9행](../fixture/decisions.md).

## 3. 서버: 반복·동시 요청과 검증 경계

BE 구현의 반환 계약과 검사 순서는 [공통 규칙](#shared)을 따른다. 소유권 검사를 취소 여부 검사보다 먼저 하므로 타인의 취소 완료 주문을 성공으로 돌려주지 않는다. 본인 주문에 순차 반복 호출을 하면 최초 변경 이후에도 같은 취소 완료 결과를 받는다.

현재 코드는 하나의 `Orders` 객체가 가진 `Lock`으로 조회·소유권 확인·상태 확인·변경을 감싼다. **같은 객체의 잠금을 공유하는 호출**은 이 구간에서 직렬 처리된다. 이는 단일 프로세스 메모리 구현의 근거다. 여러 프로세스·서버 인스턴스나 서로 다른 `Orders` 객체의 경쟁, 영속 저장소의 트랜잭션 보장을 뜻하지 않는다.

변경 대상은 전달받은 메모리 사전이다. 영속 저장 및 결제사 연동은 구현되어 있지 않으며, 성공 응답의 의미는 [공통 규칙](#shared)의 상태 변경까지다. 소스 정적 검토만 수행했으므로 실제 API 연결, 통신 장애 복구, 프로세스 재시작 후 보존, 운영 환경 동시성, 환불 실행 및 배포 성공은 입증되지 않았다. 운영 계약을 약속하려면 해당 저장·연동 설계와 실행 근거가 별도로 필요하다.

근거: [service.py 5–21행](../fixture/service.py).

## 4. 제품 판단: 문제 근거·대안·남은 결정

O1의 고객 두 명 제보에서 시작한 기능은 전체 고객 대상 관측까지 마쳤다. 취소 결과 관련 문의 비율은 전체 취소 요청을 분모로 30일간 관측한 결과 30% 감소했다. 목표였던 20% 감소를 초과 달성했으며 이는 입증된 제품 성과다.

D1은 자기 주문의 취소 상태를 직접 확인하는 제한된 기능을 우선 검토하는 안이다. 범위는 [공통 규칙](#shared)을 따른다. 결제 환불까지 제공하는 대안에는 외부 결제사 연동과 환불 정책 결정이 필요하다. 출시 일정과 출시 승인은 자료에 없다.

근거: [decisions.md O1·D1, 15–25행](../fixture/decisions.md).
